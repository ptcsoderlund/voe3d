# 0128. The cook flattens the scene, and save files are the game developer's

- **Status:** Accepted
- **Date:** 2026-09-11
- **Deciders:** Human, Tech Lead
- **Supersedes:** —
- **Superseded by:** ADR-0144, **points 1 and 2 only** — the cook emits C source and the
  compiler is the schema check, so the flattened blob and its hash are not built. **Points
  3, 4 and 5 stand**: descriptions off by default and the switch belonging to whoever
  builds, the engine taking no responsibility for save files, and why that boundary is safe

## Context

**Closes D-238**, opened by the principal's challenge on 2026-09-11: *"devs not using editor
won't use description mechanisms either?"* Nothing had decided what a shipped game actually
loads, and that is what decides whether ADR-0122's descriptions exist in a shipped binary
at all.

The fact that makes this cheap, and it is worth stating before the options: **there are two
formats and only one of them is permanent.** The *authored* format lives in git, is
hand-edited and reviewed, and must stay readable for years — ADR-0073 chose it on those
grounds. The *cooked* format is regenerated by every build, never committed and never
opened by a person. Getting the authored format wrong is expensive; getting the cooked
format wrong costs one rebuild.

Fixed by earlier decisions: ADR-0052, three builds, and cooking means building again.
ADR-0127, descriptions compile out and the struct is identical either way. ADR-0125,
references are authored ids that the loader maps. ADR-0126, the cook strips editor-only
components.

## Options considered

### Option A — the cook flattens to a blob laid out as the structs are
The game copies component tables straight in and patches references. No description in the
shipped binary, no parsing, loading is a memory copy.

### Option B — the cook writes a field-tagged binary the game reads through descriptions
Fields match by name; an unknown field is skipped and a missing one defaulted. Survives a
struct change. Costs the descriptions in every shipped binary and a parse at load.

### Option C — Option A with a schema stamp
The cook stamps the blob with a hash of the schema it was built from and the game refuses a
blob that does not match.

## Decision

**Option C**, the principal's call.

1. **The cook writes a flattened blob** laid out as the structs are, and loading it is a
   copy plus a reference fix-up. **Descriptions are not in a shipped binary.**
2. **The blob carries a hash of the schema it was cooked from, and a mismatch is refused
   loudly at load.** This is the whole of C over A: a stale blob otherwise loads silently
   and the symptom appears nowhere near the cause.
3. **Descriptions are off by default and the switch belongs to whoever is building.** A
   game developer who wants them in their own build turns them on. The engine does not
   ship them; it does not withhold them either.
4. **The engine takes no responsibility for save files.** The principal, 2026-09-11:
   *"save games we don't have to care about. That's the devs job using the engine/editor …
   we don't take any responsibility for savefiles."* A save file is runtime state chosen by
   a game — quest flags, inventory, progress — and it rarely maps onto components one for
   one. A game that wants one writes it.
5. **Point 4 is a boundary, not an obstruction.** It is only safe because of point 3: a
   developer who wants to serialise components generically can compile the descriptions in
   and do exactly that. The engine declining to own save files costs them nothing.

## Blast radius

**Cheap, and unusually so.** The cooked format is regenerated by every build and exists
nowhere else, so changing it later invalidates nothing in the wild. Point 4 is the
load-bearing half: taking responsibility for save files later is possible, and taking it
back would not be. Reversibility: **cheap for 1–3, one-way for 4.**

## Consequences

- **A shipped game loads a scene without parsing anything**, which is the point of cooking.
- **The blob is layout-specific**, so a Windows build and a Linux build may need different
  blobs. The hash makes that a clear refusal rather than a mystery, but cooking becomes
  per-platform and that needs to be true in the build before `dev_editor` ships anything.
- **Descriptions must exist during the cook**, so the cook is a build that has them on. The
  editor already is one.
- **A developer wanting save files gets no help and no hindrance.** Where user data belongs
  on disk is a genuinely platform-shaped question and the only folder allowed to know is
  `platform` — recorded as D-240 behind the file API, which the principal has parked.
- **Nothing here changes ADR-0118's asynchronous loading contract**, which is parked and
  concerns a different tier of asset.

## Rejected options and why

**A alone.** Rejected on one failure: a stale blob loads silently and corrupts everything
downstream. The hash is a few lines and converts the worst debugging experience this design
can produce into an error message.

**B — descriptions in the shipped game.** Rejected on the principal's own reasoning, which
was correct: the consumers of a description are the inspector and the cook, both of which
are authoring tools. Putting them in every shipped binary to serve a save-game feature that
does not exist, for an engine that does not own save games, is paying for a caller nobody
has. Point 3 leaves the door open for anyone who disagrees in their own build.
